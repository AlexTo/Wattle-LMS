Instructors keep editing a course after it's published. This design makes those edits safe for students who are already enrolled: nothing half-built becomes visible, nothing a student has done is lost, and progress stays correct.

In a draft course every change applies immediately and delete is a hard delete: a draft has never been open to students, so nothing there can affect them. Everything below applies to published and archived courses, since both can have students with progress and attempts.

## Workflow

### Lifecycle of a course

```d2 title="Lifecycle of a course: a draft is published once it has content; archiving keeps whether it was ever published, and restore returns it there"
direction: right

new: "Created" {shape: oval}
draft: Draft
published: Published
archived_draft: "Archived\n(never published)" {style.stroke-dash: 3}
archived_published: "Archived\n(was published)" {style.stroke-dash: 3}

new -> draft
draft -> published: "publish\n(needs a content item)"
draft -> archived_draft: archive
published -> archived_published: archive
archived_draft -> draft: restore
archived_published -> published: restore
```

- Only a **draft** can be published, and only once it has at least one content item, so a course is never opened up empty. Publishing is refused for an archived course: restore it first.
- The course records `publishedAt` the first time it's published and never clears it. That is how an archived course remembers whether it was ever open to students: **restore returns a course that was published to Published, and one that never was to Draft.** A course students have used never goes back to draft, where delete is permanent.
- Repeating an action writes nothing: publishing a published course, or restoring a course that isn't archived, returns the course as it is. A retry after a timeout is safe.
- Each change is conditioned on the status it read, so two requests can't overwrite each other: if the course changed to something else in between, the request returns `CONFLICT`.
- Publishing a course doesn't change any record under it. A draft course's modules, lessons and content items are already `visible`, so they become visible to students together with the course.

### Lifecycle of a module, lesson or content item

```d2 title="Lifecycle of a module, lesson or content item: the course's status decides where a new record starts and what delete does; then publish, hide, archive, restore and delete"
direction: down

new_draft: "Created in a\nDraft course" {shape: oval}
new_live: "Created in a Published\nor Archived course" {shape: oval}

live: "Not archived" {
  visible: Visible
  hidden: Hidden

  hidden -> visible: publish
  visible -> hidden: hide
}

archived: "Archived\n(frozen until restored,\nwith everything under it)" {
  style.stroke-dash: 3
}

deleted: Deleted permanently {shape: oval}

new_draft -> live.visible
new_live -> live.hidden
live -> archived: "delete\n(course not Draft)"
archived -> live: restore
live -> deleted: "delete\n(course Draft)"
archived -> deleted: "delete permanently\n(see below)"
```

- The diagram follows one module, lesson or content item. The course's own status (Draft, Published or Archived) is a separate thing (see above), and none of these actions change it. It only decides where a new record starts, and whether delete archives the record or removes it.
- Students see a record only while it's **Visible** and every ancestor is too (see [Effective visibility](#effective-visibility)).
- Publishing a module or lesson also publishes every hidden, unarchived record under it, including ones that were hidden on purpose. Hiding, archiving and restoring change only the record itself.
- An archived record keeps its visibility, so restoring it brings it back **Visible** or **Hidden**, as it was. It can only be restored once its parent module or lesson isn't archived.
- An archived record, and everything under it, is frozen: nothing in it can be published, hidden or edited, and nothing can be added to it.
- Outside a draft course, every change to what students can see triggers a progress recalculation for everyone enrolled.

```d2 title="Checks a permanent delete goes through before anything is removed, for a module or lesson and for a single content item"
limit: "More than 100 records\nincluding everything\nunder it?" {shape: diamond}

refused_archive: "PRECONDITION_FAILED:\narchive it first"
refused_activity: "PRECONDITION_FAILED:\nit can stay archived,\nbut is never deleted"
refused_limit: "PRECONDITION_FAILED:\ndelete some of its lessons\n(or content items) first,\nthen retry"

start -> is_archived
is_archived -> refused_archive: no

activity -> refused_activity: yes

```

## Data model

Attributes on the `curriculum` entities that support live editing:

| Attribute | On | Purpose |
|---|---|---|
| `visibility: 'hidden' \| 'visible'` | Modules, lessons, content items | Required. Create procedures set `visible` in draft courses and `hidden` in every other course, so a new quiz, lesson or module is never seen half-built. The instructor clicks **Publish** to show it |
| `archivedAt` | Modules, lessons, content items | Soft delete. Set only on the archived record itself; its children are hidden because their parent is archived, not by being archived themselves |
| `studentActivityCount` | Content items | Number of distinct students with any data for the item. Incremented (`ADD 1`) in the same transaction that creates a student's **first** record for the item: the per-user quiz summary for a quiz, the `itemCompletion` for video or text. Never decremented |

`studentActivityCount` lives in the curriculum partition, so summing or checking it for everything under a module or lesson is one query. The student-side records it counts are keyed by user and can't answer "who used this item?" without a scan.

## Effective visibility

A record is shown to students only if it and every ancestor are `visible` and not archived. This is checked on:

- every student read: core-api's `course.view` and `course.publicView`, and `quiz.view`;
- every student write: quiz submission, marking an item complete;
- every progress calculation.

The rule is implemented once, as `filterEffectivelyVisible` in `@discava/core-table`, next to the attributes it interprets. core-api's course views use it, and so does the progress recalculation Lambda in `packages/events`, so what students see and what their progress counts can never disagree.

So hiding or archiving a module also stops a quiz inside it being submitted, and removes its items from everyone's progress.

Instructors edit through instructor-api's `course.view`, which returns the whole curriculum, including hidden and archived records along with their `visibility`, `archivedAt` and `studentActivityCount`. It's limited to instructors teaching the course. The course editor leaves archived records out of the main list and marks hidden ones **Hidden**.

## Actions in a course that isn't a draft

| Action | What students see | Their data and progress | Progress recalculated for |
|---|---|---|---|
| **Add module** | Nothing until published. Publishing also publishes its hidden lessons and items, so it appears all at once | Once published, `progressPercent` drops for everyone. Completed lessons and courses stay completed | All enrolled students, on publish |
| **Remove module** | Archived: gone from the outline on next load. A student on one of its pages gets "This lesson has been removed by your instructor" | Kept (completions, attempts, best scores), no longer counted. A student who had finished everything else becomes `completed`. Restorable, and then it all counts again | All enrolled students |
| **Edit module** (title, description, order) | Applies immediately | No effect | No one |
| **Add lesson** | Nothing until published (together with its hidden items) | As for adding a module | All enrolled students, on publish |
| **Remove lesson** | As for removing a module | As for removing a module | All enrolled students |
| **Edit lesson** (title, description, order) | Applies immediately | No effect | No one |
| **Add content item** | Nothing until published, and only once its lesson and module are published too | Once published, `progressPercent` drops. If its lesson was already completed, the lesson stays completed and the item shows as **New** | All enrolled students, on publish |
| **Remove content item** | Archived: disappears on next load. Submitting a quiz in it or marking it complete is rejected with "no longer available" | Kept, not counted. If it was a student's only unfinished item, the lesson (and possibly the course) becomes completed. Restorable | All enrolled students |
| **Edit content item**: title, description, text body | Applies immediately | Completion kept | No one |
| **Edit content item**: replace video | Goes through the video replace and re-transcode flow | Completion kept | No one |
| **Edit content item**: quiz | See <Link path="design/quizzes">Quizzes</Link>: answer-key-only edits are invisible; question edits make an in-progress submit return `CONFLICT` | Attempts, best scores and passes kept, never regraded | No one |
| **Hide** (any level) | Disappears like a removal, but isn't in the Archived view | Kept, not counted; counts again when shown | All enrolled students |
| **Reorder** (any level) | Applies immediately | No effect | No one |

"Progress recalculated" is done by the server-side Lambda described in <Link path="design/progress-and-completion">Progress and completion</Link>, never by the student's browser.

## Publishing

Publishing a module or lesson sets it and all of its hidden descendants to `visible` in **one transaction**, so students see a new lesson with all its items at once rather than piece by piece. Archived descendants, and content items under an archived lesson, are left as they are. That holds even if one is archived while the publish is in flight: every lesson and item it changes (and the lesson of every item it publishes) must still be unarchived when the transaction commits, otherwise nothing is published and the request returns `CONFLICT`. Retrying re-reads the module or lesson and skips the newly archived record.

That includes descendants that were hidden on purpose: publishing a module or lesson always publishes everything hidden under it. To keep a lesson or item back, hide it again after publishing its parent.

Hiding is not cascaded: it changes only the record itself, and its children keep their own `visibility`. Students stop seeing the children anyway, since a record is only shown under visible ancestors.

## Removing (archiving)

Outside a draft course, delete always archives, and the instructor portal labels the action **Archive** (in a draft course it's **Delete** for modules and lessons, and **Remove** for content items). The confirmation dialog shows the impact from `studentActivityCount`:

- a content item: "12 students have attempted this quiz. Their results will be kept."
- a module or lesson: the sum over the items underneath, worded "about N students", since a student active in several items is counted once per item.

### Removed while a student is learning it

| Where the student is | What happens |
|---|---|
| Elsewhere in the course | The module or lesson is gone from the outline the next time it loads |
| On that lesson's page | Content already on screen stays readable. The next data refetch (navigation, window focus) shows **"This lesson has been removed by your instructor"** with a link back to the outline, never a bare 404 |
| Partway through a quiz in it | Submit is rejected ("This quiz is no longer available"); local draft discarded; no attempt used |
| Marking an item complete | Rejected the same way |
| Old link or bookmark | The same "removed" page |

The archive triggers a progress recalculation for every enrolled student, so the removed content stops counting straight away, without anyone reloading.

### What can't be done to an archived record

An archived record, and everything under it, stays exactly as it was archived until it's restored, so a restore brings back what students saw. All of these are refused with `PRECONDITION_FAILED`:

- Publishing, hiding or editing the archived record itself: "Restore the module (lesson, content item) before publishing (hiding, editing) it".
- Publishing, hiding or editing anything under it, e.g. a lesson in an archived module or a content item in an archived lesson: "Restore the module first" or "Restore the lesson first". The module is named first when both are archived.
- Adding anything under it: no new lessons in an archived module, and no new content in an archived module or lesson.
- Uploading a video file: no upload URL is issued for an archived module or lesson, or to replace the file of an archived content item.

Records under an archived module or lesson can still be archived themselves, and then deleted permanently.

These rules hold even when requests overlap. Each write under a module or lesson runs in one DynamoDB transaction, together with checks that its module (and lesson) still exist and aren't archived, and that the record itself isn't archived. If another request archives or deletes the parent in between, the whole write is refused with the same error, and nothing is written. So a module that's being archived or permanently deleted can't gain a new lesson, and a lesson can't gain a new item, at the last moment.

A video archived while it's still transcoding keeps transcoding. When the job finishes, the item is marked `ready` (or `failed`) without touching `archivedAt` or `visibility`, so it plays if it's restored and stays hidden until then.

## Restoring

The instructor course page has an **Archived** section, grouped by module and lesson, with **Restore** on every row.

- Restoring clears `archivedAt` and returns the record to its original `order`.
- A lesson can only be restored if its module isn't archived, and a content item only if neither its module nor its lesson is. Otherwise it's refused with "Restore the module first" or "Restore the lesson first", naming the module first when both are archived. The view offers to restore the parents too.
- A restored quiz keeps its version, attempts and best scores.
- Restoring triggers a progress recalculation, and everything counts again as before.

## Permanent delete

Offered only from the Archived view, for a record that is itself archived (one under an archived parent must be archived first), and only when `studentActivityCount` is 0 for the item, or for every item under a lesson or module. Anything a student has used can be archived but never permanently deleted.

The checks and the delete are separate calls, so the delete itself carries conditions:

- **A module or lesson** is deleted with everything under it in one transaction. Each content item's delete is conditioned on the `updatedAt` that was checked (a student's first activity bumps it), and the module or lesson's own delete on the `archivedAt` that was checked, so a restore landing in between cancels it. Lessons under a module are deleted without a condition of their own.
- **A single content item** is one delete, conditioned on `studentActivityCount = 0` and the item still being archived.

If a condition fails, the delete is refused with `CONFLICT` and nothing is removed. Any other failure of the transaction is reported as `INTERNAL_SERVER_ERROR`, also with nothing removed.

## Limits and repeated requests

- **Whole sets only.** Publishing a module or lesson and deleting one (in a draft course or permanently) read every page of descendants, not just the first 1 MB, so nothing is left unpublished or orphaned. Both `course.view`s read every page of the curriculum too.
- **100-item transactions.** Publishing a module or lesson, and deleting one (in a draft course or permanently), happens in a single all-or-nothing DynamoDB transaction, which holds at most 100 records. A larger module or lesson can still be published or deleted, just in steps:
  - publish some of its lessons (or content items) first, then the module (or lesson);
  - in a draft course, delete some of its lessons (or content items) first, then the module (or lesson);
  - otherwise, archive some of its lessons (or content items) and delete them permanently first, then the module (or lesson).

  When an operation would go over the limit, it's refused with `PRECONDITION_FAILED` and a message naming that next step. It's never split into several transactions behind the scenes: if one of them failed, part of the module would already be gone, leaving lessons or items with no parent.
- **Repeats write nothing.** Archiving something already archived keeps its original `archivedAt`. Publishing a content item that's visible, or a module or lesson with nothing hidden in or under it, hiding what's hidden, and restoring what isn't archived all return the record unchanged. A retried request, e.g. after a client-side timeout, is harmless. The exception is a delete that removes the record (in a draft course, or permanently): retrying it returns `NOT_FOUND`, since the record is already gone.
