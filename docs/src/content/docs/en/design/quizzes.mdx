A quiz is a content item (`type: 'quiz'`) placed in a lesson's sequence alongside video and text. It has one or more questions, each **single choice** or **multiple choice**.

## Data model

### Quiz content item

Quiz-specific `contentItem` attributes. As with video and text, which attributes a type requires is enforced by the zod schemas, not by ElectroDB.

| Attribute | Shape |
|---|---|
| `questions` | `[{ questionId, kind: 'single' \| 'multiple', prompt, options: [{ optionId, text }] }]`. `prompt` is Tiptap JSON. Safe to send to students |
| `answerKey` | `{ [questionId]: { correctOptionIds: string[], explanation? } }`. `explanation` is Tiptap JSON. **Never read by core-api except when grading** |
| `settings` | `{ passMarkPercent, attemptsAllowed /* null = unlimited */, shuffleOptions, revealAnswers: 'after_each_attempt' \| 'after_final_attempt' \| 'never' }` |
| `quizVersion` | Number, incremented on every save. A save names the version the editor loaded, and is refused if the quiz has moved on (see [Saving a quiz](#saving-a-quiz)) |
| `questionsHash` | Hash of `questions` only (not `settings`), recomputed on every save |

`questions` and `answerKey` are separate attributes so that passing a content item through to students can't leak the answers. Course reads (`course.view`, `course.publicView`) list a quiz by its title and position only; they never include `questions` or `answerKey`.

`questionId` and `optionId` are supplied by the client and must stay the same across saves, because the answer key, student answers and the reconcile step below all refer to them.

### `quizAttempt`

- pk `userId`, sk `courseId / contentItemId / attemptId`.
- Holds `answers` (`{ [questionId]: optionId[] }`), `scorePercent`, `passed`, `quizVersion`, `questionsHash`, `submittedAt`.

### Per-user quiz summary

- Holds `attemptsUsed`, `bestScore`, `bestAttemptId`, `passedAt`.
- Written in the same transaction as each attempt, conditioned on `attemptsUsed < attemptsAllowed`, so the attempt limit holds even when two submissions race.
- `bestScore` only increases. `passedAt` is set by the first passing attempt and never cleared.
- Creating a student's summary increments the quiz's `studentActivityCount` (see <Link path="design/live-course-editing">Live course editing</Link>).

## Grading

- Server-side only, in core-api. The client never receives `answerKey` before submitting.
- Each question is all-or-nothing: the selected options must exactly equal `correctOptionIds`.
- Score is the percentage of questions correct; `passed` is `score >= passMarkPercent`.
- The **best** score across all attempts, and across quiz versions, is the one that counts.
- A recorded pass is permanent, even if the pass mark is later raised or the quiz is edited.
- Past attempts are never regraded automatically.

## Quiz edited mid-attempt

With each submission the client sends the `questionsHash` of the questions it showed.

| What the instructor changed | Result of submitting |
|---|---|
| Only the answer key or explanations (hash matches) | Accepted and graded against the **current** key. The student notices nothing |
| Any prompt, question kind, or option's wording, count or order (hash differs) | `CONFLICT`, and **no attempt is used**. The client refetches and reconciles (below) |
| Pass mark | Accepted and graded against the current pass mark. A pass already recorded stays |
| `attemptsAllowed` lowered to or below `attemptsUsed` | Rejected with "No attempts remaining", showing the best score |
| Quiz, or its lesson or module, archived or hidden | Rejected with "This quiz is no longer available"; local draft discarded |

"Answer-key-only" means the student's screen would look identical before and after. Examples:

- Correcting which option is right: the key said EC2 for "Which service runs containers without managing servers?", and it's corrected to Fargate.
- Adding another correct option to a multiple-choice question. The screen doesn't change, because it always says "Select all that apply" and never how many are correct.
- Adding or rewording an explanation.

Reordering options counts as a change even though it's harmless, to keep the rule simple: if the screen could look different, the student reviews.

### Reconciling after `CONFLICT`

The client compares the old and new `questions` by `questionId`:

- **Unchanged:** the answer is kept.
- **Removed:** the answer is dropped.
- **New:** starts unanswered, marked **New**.
- **Changed prompt, options or kind:** answers pointing at options that still exist are kept (for a question switched to single choice, only if exactly one remains), and the question is marked **Updated**.

The student lands on the review screen with "This quiz was updated. Check the marked questions before submitting." The quiz query also refetches when the review screen opens and on window focus, so the banner usually appears before they press Submit; the `CONFLICT` is the guarantee.

## Student experience

The lesson is one scrolling page with items in `order`. A step bar at the top shows each item's state (✓ done, ⚠ finished but not passed, ○ not attempted) and jumps to it. **A failed quiz never blocks moving on.**

The quiz is a card in the lesson flow:

```
┌ Quiz: Module 3 check ─────────────────────┐
│ 5 questions · Pass 80% · 1 of 3 attempts  │
│ Best score: 60%              [Retake quiz]│
└───────────────────────────────────────────┘
        ↓ start
┌ Question 2 of 5        ● ● ○ ○ ○          ┐
│ Which are AWS serverless compute?         │
│ Select all that apply                     │  ← multiple choice only
│ ☐ Lambda   ☐ EC2   ☐ Fargate              │  ← checkboxes vs radios
│                     [Back]  [Next]        │
└───────────────────────────────────────────┘
        ↓ review screen (unanswered flagged) → Submit
┌ Best: 80% · Passed ✓ ─────────────────────┐
│ This attempt: 60%                         │
│ Per-question ✓/✗ + explanation            │  ← per revealAnswers
│            [Retake quiz]  [Continue →]    │  ← equal weight
└───────────────────────────────────────────┘
```

- One question per screen inside the card, with a dot navigator and a review step before submitting.
- Multiple choice is visually distinct: square checkboxes and "Select all that apply".
- Feedback only after submitting, never per question, so the key can't be probed one option at a time.
- In-progress answers are saved to localStorage per quiz. The attempt is created on the server only on submit.
- A lower retake shows "Your best score of 80% still counts."
- Accessibility: a `fieldset`/`legend` per question, right and wrong shown with an icon and text (not colour alone), full keyboard support.
- Prompts and explanations use a read-only Tiptap renderer, shared from `common/shadcn`.

## Saving a quiz

Creating a quiz, and every later save, writes the whole quiz as one document. `quizVersion` is how two editors, or a stale tab, are kept from overwriting each other.

```d2 title="What happens when an instructor saves a quiz: access and archive checks, the version check, then one conditional write"
direction: down

start: "contentItem.updateQuiz\n(sends the quizVersion\nthe editor loaded)" {shape: oval}
access: "Instructor of this\ncourse, and the item\nis a quiz?" {shape: diamond}
archived: "Quiz, its lesson, module\nor course archived?" {shape: diamond}
stale: "Stored quizVersion\n= the one sent?" {shape: diamond}
write: "One transaction: course, module and lesson\nstill exist and aren't archived, quiz isn't\narchived and is still at that quizVersion.\nWrites the new content, quizVersion + 1\nand the recomputed questionsHash"
landed: "Did a condition fail?" {shape: diamond}

forbidden: "FORBIDDEN or BAD_REQUEST"
frozen: "PRECONDITION_FAILED:\nrestore it first"
conflict: "CONFLICT: the quiz changed since it\nwas loaded; reload and retry.\nNothing written"
done: "Saved as quizVersion + 1" {shape: oval}

start -> access
access -> forbidden: no
access -> archived: yes
archived -> frozen: yes
archived -> stale: no
stale -> conflict: no
stale -> write: yes
write -> landed
landed -> conflict: "yes, and nothing is archived"
landed -> frozen: "yes, and something was archived"
landed -> done: no
```

- Of two saves made from the same version, exactly one lands; the other gets `CONFLICT`. The check is repeated inside the write's transaction, so it holds when the saves are simultaneous, not only when one follows the other.
- A save that succeeds returns the new `quizVersion`, which the editor uses for its next save.
- `questionsHash` is recomputed from `questions` only, so a save that changes just the answer key, explanations or settings keeps the same hash.
- Creating a quiz starts it at `quizVersion` 1. Like other new content, it starts `visible` in a draft course and `hidden` otherwise, and it can't be created or edited under an archived module or lesson, or in an archived course (see <Link path="design/live-course-editing">Live course editing</Link>).

## Instructor experience

- A **Quiz** button sits next to the **Video** and **Text** buttons in the lesson's content row. It opens the builder for a new quiz, which is created on its first save.
- The builder is its own route (`/my-courses/$courseId/quiz/$contentItemId`), not a dialog:
  - Settings: title, description, pass mark, attempts allowed, shuffle options, when to reveal answers.
  - A card per question: Tiptap prompt (the editor is mounted only for the expanded card), Single/Multiple toggle, option rows with a correct marker (radio for single, checkbox for multiple), add/remove/reorder options, optional explanation.
  - Drag to reorder questions.
  - **Preview as student**, using the real student component.
  - The whole quiz saves as one document: `contentItem.updateQuiz` replaces questions, key and settings together, against the `quizVersion` the builder loaded. On `CONFLICT` the builder offers to reload the latest version.
  - Read-only, with the reason, while the quiz or anything above it is archived.
- Validation, in the form and in zod (the API enforces all of it, whatever the form does):
  - 1 to 50 questions, each with 2 to 10 options. Option text is 1 to 500 characters.
  - Single choice: exactly 1 correct. Multiple choice: at least 1 correct. Every correct id is one of the question's options.
  - Every question has an answer key entry, and the key has no entries for other questions. Question ids are unique, and option ids are unique within a question.
  - Prompts and explanations are Tiptap documents that conform to the editor's schema (the same `StarterKit` nodes and marks), stored as JSON strings.
  - Pass mark is a whole number from 0 to 100. Attempts allowed is a whole number from 1, or unlimited.
  - Questions and answer key together are at most 300 KB, well under DynamoDB's 400 KB item limit.
  - Switching Multiple → Single with more than one correct asks which to keep.
- Editing a quiz that has attempts warns "N students have attempted this quiz".
